# 上游提供商契约

只读取本次涉及的提供商章节。通用协议转换见 [protocol.md](protocol.md)，故障切换及 OAuth 凭证终态禁用见 [proxy.md](proxy.md)，配额累计见 [billing.md](billing.md)。省略目录的 app 文件位于 `internal/app/`；文中的渠道禁用、连接轮换等跨专题机制按这些链接查阅。

审查或修改 wire 形态、指纹、签名及发送前处理时，先读该节记录的参照上游固定提交（如"对照来源"）中的对应实现，列出其完整分支表后再与本地比对，不凭推理判定"方向错误"。本地的典型偏差是只移植了命中当前场景的分支。

## Accio

- 所有出站接口统一使用不含 ccLoad 标识的标准 Chrome UA，共用 JSON Content-Type/Accept、`Accept-Language/x-language: en`、`x-platform: desktop`、`x-os`（macOS 为 `macos`）、`x-app-version: 0.34.4` 与地区头；推理另设 SSE Accept、`version: 0.34.4` 和 `appKey: OneChat`。2026-11-07 国际版同账号同出口对照：推理 `undici` 返回 `Bxpunish: 1` HTML，仅换 UA 可恢复 SSE，只改版本或 appKey 仍被拦截；不再保留 `undici` 或 Go 默认 UA。控制面错误展示真实 HTTP 状态与数字业务码，重试分类仍用归一状态，不回显原始响应消息。
- Accio 先将 `system` / `developer` 文本中的 `Claude`、`Codex` 大小写敏感替换为 `Accio`，再复用 `antigravity_sensitive_words`。后者仅处理 `system` / `developer` 消息字符串和 text 内容块；在渠道请求体规则之后、ADK 编码之前插入零宽字符，正常代理与管理测试共用入口。空数组只禁用零宽处理，名称替换仍生效；敏感词配置修改后重启生效。
- `accio_oauth` 对 Registry 暴露逻辑 OpenAI Chat。支持显式 `region=cn|global` 的 PKCE 网页授权及 canonical/官方 camelCase JSON 凭据导入，无签到；按地区与用户标识账号。重新导入保留模型配置，目录批量导入按身份去重。
- 网页授权复用 Codex OAuth 管理器的启动、回调、状态、取消及生命周期：国内登录 `www.accio-ai.com/login`，国际登录 `www.accio.com/login`，客户端 `accio-work`；随机本机端口接收 `/auth/callback-accio`，远程部署可提交完整回调 URL。`return_url` 与换码 `redirectUri` 逐字相同；state 一次性消费，PKCE verifier 留在服务端。
- 国内国际共用 `phoenix-gw.alibaba.com`，`x-package-region` 分别为 `CN` / `GLOBAL`。用户资料 `/api/auth/userinfo` 使用 POST JSON `accessToken`（2026-10-20 实测纠正参考项目 GET 导致的 405）；额度与订阅 GET 使用 query `accessToken`，刷新 POST 使用 body `accessToken/refreshToken`；不携带 Bearer。临期一分钟刷新、401/403 单次刷新、singleflight 与 CAS 保留新凭据及并发额度快照。
- 目录 `POST /api/llm/config` 获取可见对话模型，公开 ID 与推理 body 的 `model` 统一使用目录 `modelName`，列表按名称去重、不生成编码重定向，缺少名称的条目跳过。不解析或匹配 `modelCode`，旧编码重定向不兼容；不使用静态别名或兜底模型。目录按渠道/地区/用户缓存一小时并绑定访问令牌指纹，避免换凭据仍用旧能力。
- `accio_wire.go` 在统一出站边界构造 ADK `/api/adk/llm/generateContent?sg_k=md5(request_id)` 请求；认证 token 仅放实际请求体，逻辑请求留给调试/重试/转换。消息、工具及思考参数转原生字段，思考落点由模型目录 `protocol` 决定。
- Accio 会话字段 `session_key`、`conversation_id/name` 在跨协议转换后、渠道 BodyRules 前从原始 body 补回；接受驼峰及 `session_id/sessionId` 别名，按原生名优先取首个非空字符串并去首尾空白。非字符串报错；重试不恢复规则已删除的字段，不从头部推导会话。每次 `request_id/message_id` 仍独立生成。
- 推理携带 `utdid`：官方 JSON 的 `utdid/deviceId` 保存为 `device_id`；缺少时按地区+已验证用户标识派生稳定 desktop 标识，刷新令牌不改变设备身份，重新授权缺项保留已有设备值。2026-10-20 实测缺该头会返回 HTTP 200 HTML + `Bxpunish: 1`；补头后进入真实 SSE，但测试环境仍收到业务码 555 / sentinel rate limit（映射429）。管理测试诊断记录实际原生请求，body token 与设备头脱敏；网关挑战先分类为502并剔除挑战Cookie/跳转地址，不误报EOF或刷新令牌。
- 官方 `sgcookie/sgCookie` 经导入、OAuth 换码和刷新保存为可选 `sgcookie`，仅随推理发送同名头并在调试输出脱敏；缺项保留已有值，拒绝超过4096字节或非可见 ASCII 的值。刷新期间仅更新 cookie 时保留最新 cookie 并发布已轮换令牌，不能把 cookie 更新误判为新授权而丢弃已消费刷新令牌的结果。
- 正常推理响应为 SSE，转换成 Chat SSE 后复用现有协议转换及非流式聚合器；空 `content` 对象允许缺少 `parts` 或 `parts: null`，仍处理同帧终态与 usage，除 `null` 外的非数组 `parts` 拒绝。保留工具参数与 usage，缺失终态的 EOF 返回错误，已有输出后不重放。原生业务错误映射 401/429/502，SSE 错误携带顶层 status 供通用分类器识别。
- 普通 `text` 中的 `<think>` / `<thinking>` 按流状态拆为正文和 `reasoning_content`，支持标签跨原生帧；`thought: true` 的结构化思考保持原文。工具、结构化思考和流终止前排空残留标签片段，保留输出顺序、签名与错误终态；管理测试页使用相同解析器。
- 额度以百分比窗口展示，订阅字段保留原单位；只保存安全 `oauth_usage` 快照，不进入 USD 窗口成本账本。控制面错误不回显令牌/query URL，禁止跟随重定向。
- 参考提交及独立实现边界见 `internal/accioauth/UPSTREAM.md`；使用说明见 `docs/guide/accio.zh-CN.md`。

## Qoder

- `qoder_oauth` 使用显式 `region=cn|global`，支持 PKCE、PAT、canonical JSON；账号按地区与用户区分。网页保留 device-token 单对；PAT 的 job refresh 被401/403拒绝后可重新兑换并核对身份，发布复用共享刷新/CAS。canonical到期时间仍存Unix秒，上游期限兼容见 [来源及分支表](../../internal/qoderauth/UPSTREAM.md)。
- 参照 Magpie 插件 `52e31c4a1fdb857d673c6e92c90ef4a6c1294c68`。国内门户 `qoder.cn`、国际 `qoder.com`，带官方client_id；国内推理/目录在gateway.qoder.com.cn，国际统一api3.qoder.sh。App身份、COSY1.1.69、ClientType10；推理不伪造机器风控token，也不运行/安装UMID。
- 目录App优先、Chat补充，同key取App；过滤禁用与auto/default，保留旧显示名归一的公开ID，同名后续条目用原生key。缓存绑定渠道/地区/用户/访问令牌，一小时失效；缺项重取，确认额度耗尽的禁用模型返回429，异常免费视图最多每五分钟尝试一次刷新。
- 渠道BodyRules及system/developer零宽处理之后，前置Qoder默认身份并合并原system/developer；用户/工具内容不做敏感词改写。编码及COSY签名后不改body。正常代理与管理测试共用此入口。
- 请求支持稳定会话、用户轮任务复用、business.model_key和原生缓存标记；任务缓存账号隔离、512项/空闲2小时。按目录选思考档/输出上限，短预算默认关闭或最低思考档；上下文粗估包括输出预算。工具历史ID、图片、推理别名及schema按来源分支表处理。
- 原生SSE归一后进入已有转换器；工具文本仅匹配已声明工具，保留代码示例；处理迟到名称和同index不同ID，纯无名调用报502。保留多choices、严格帧校验和无终态EOF报错；输出后不重放。非流式复用Chat聚合器。
- 排队仍按503交统一路由，不在插件内长时间轮询。普通认证403归一401并单次刷新；明确请求错误归一400，供应商内部错误502；明确输出上限拒绝仅同渠道降额修复一次，不跨请求学习上限。
- 额度仍从 `/api/v2/quota/usage` 获取原生credits，保存oauth_usage安全快照，不进入token成本账本。签到仍是campaign列表/claim及同活动回查，不伪造奖励。已启用渠道自动签到，UTC+8 10点窗口去重、启动约一分钟补扫、每15分钟复查。
- 国际签到依赖官方UMID，并先从Sash取UID；桌面/CLI组件环境参数均为3。发现官方安装与CLI缓存，支持其目录环境变量。Linux/macOS amd64/arm64缺组件时下载官方npm包、校验SHA-512并原子安装到data/qoder-umid/runtime-info；Windows只复用官方安装组件。保留后台安装、进度轮询、取消及生命周期契约，容器需glibc/libstdc++/libgcc。

## CodeBuddy

- `codebuddy_oauth` 渠道支持扫码登录、workbuddy.json / canonical JSON 导入与自动刷新。登录 state 和 CookieJar 按管理员会话隔离，轮询最长 5 分钟；相同 UID + enterprise_id 重新授权更新已有渠道。
- 默认精确端点 `https://copilot.tencent.com/v2/chat/completions`，OpenAI 上游、本地协议转换。上游始终 `stream:true`；非流式调用通过共享 SSE 读取器聚合，保留工具参数、思考内容、结束原因及尾部 usage。读取到 `[DONE]` 停止；缺少 `[DONE]` 时仅接受已有完成标记的 EOF。
- 两句 Claude Code 固定文本仅在消息文本内精确替换：`You are Claude Code, Anthropic's official CLI for Claude.` → `You are CodeBuddy Code.You are an interactive CLI tool that helps users with software engineering tasks.`，`Main branch (you will usually use this for PRs)` → `Default branch (you will usually use this for PRs)`。工具结果和函数参数不改写。hy3 系列仅在调用方未指定思考选项时默认 `reasoning_effort:high`，渠道请求体规则可覆盖。
- **Chat 出站兼容**（`finalizeCodeBuddyBody`，参考 magpie-community/plugins `b4916d414321bff0ffdf0f43af7d14e37b540789`，范围与分支见 `internal/codebuddyauth/UPSTREAM.md`）：渠道 BodyRules 后，首条不是 system（包括 developer）时前置默认 system，再将所有 `developer` 转为 `system`；`max_completion_tokens` 迁到 `max_tokens`，已有后者优先。助手历史优先保留非空 `reasoning`，否则取 `reasoning_content` 或依序拼接 `reasoning_details` 的 text/summary，并删除两个别名。只在 system/assistant 文本内对已知 DSH 开场白、Web GUI 说明做局部改写；完整 `Tokens prefixed with @ ... workspace root` 片段仅在开头 T 后插入 U+034F，保留 workspace、路径或工具数据。普通代理和管理测试共用此最终化入口；不隐藏任意品牌名，不将 system 降级成 user。
- **11128 身份句修复**（`codebuddy_retry.go`）：普通代理在未提交响应的 HTTP 400 或 CodeBuddy SSE 错误中确认结构化 code=11128 时，只对 system/assistant 的身份句连接词前加逗号，同渠道同 Key 重试一次，使用实际发送体且不重复应用 BodyRules。匹配 `You are a/an/the … agent/assistant powered by/running on/running in/built on/based on`；用户、工具、非文本块及工具定义不改。完整成功且 system 确有改写才记忆，assistant-only、失败、截断或取消不学习。服务实例内最多保存 256 个 SHA-256 摘要，按渠道 ID、上游 origin、实际模型与完整 system 消息隔离，FIFO 淘汰、重启清空；命中后在最终隐私遮蔽之后预先改写。仅明确错误码触发，不按宽泛错误文案重试。重试日志策略为 `pause_codebuddy_identity`。
- CodeBuddy 与 Antigravity 共用 `antigravity_sensitive_words` 设置及匹配器，统一在命中词首 rune 后插入 U+034F（组合字素连接符），不区分提供商。Antigravity 仅处理 `systemInstruction`；CodeBuddy 在固定文本替换后仅处理 `system` / `developer` 消息的字符串或内容数组文本；不改写用户/助手消息、工具参数及工具结果。空数组禁用，修改后重启生效，正常代理与管理测试共用最终化入口。2026-11-11 实测原 U+200B 混淆在 Antigravity 系统提示中触发 429，完整请求改为 U+034F 后成功；CodeBuddy DeepSeek 完整请求重放同样成功。
- 已知到期时间提前 60 秒刷新，HTTP 401 时强制刷新后重试一次；并发刷新按渠道和被拒 Token 合并，全凭证 CAS 保存，重新授权结果优先。刷新任务归服务器生命周期，单个请求取消不取消共享刷新。
- Bearer 和 X-Refresh-Token / 账号身份头由渠道凭证生成，刷新令牌禁止自定义规则覆盖并在调试输出脱敏；计费签到/余额请求使用独立头部，绝不携带 `X-Refresh-Token`。“获取模型”通过官方 CLI 的 `GET /v3/config` 读取 `data.models[].id`，使用账号凭证和渠道代理；已保存渠道在 401 时刷新后重试一次，失败或空目录直接报错，不回退内置列表。浏览器 OAuth、认证文件及批量凭证导入新建渠道共用该模型查询、过滤和排序逻辑，查询失败不创建渠道；已有渠道重新授权保留自定义模型配置。余额通过 `www.codebuddy.cn` 的 `daily-checkin` / `get-user-resource` 接口查询，结果进入 OAuth 用量快照并纳入单个、批量和活跃渠道额度刷新；管理端可通过 `POST /admin/channels/:id/codebuddy-checkin` 立即签到并同步余额。
- 来源及许可见 `internal/codebuddyauth/UPSTREAM.md`。未修改 CLIProxyAPI 核心快照。

## OpenCode Zen / Zen Go

- **API Key 渠道**：管理页「添加」统一提供 OpenCode 入口，点击后选择 Zen / Zen Go，再打开预填的渠道表单；生成名称使用 `OpenCode-Zen`、`OpenCode-Zen-Go`。官方 OpenCode URL 渠道不支持管理账户：前端隐藏分区、导航及列表入口，编辑器未加载账户时保存不提交该字段（不清除服务端值）；后端（`supportsChannelManagement`）按规范化后的 URL 拒绝带 `management_account` 的创建/更新（409），详情不返回、余额/签到接口与定时签到跳过，已存封套不删除，URL 改回非 OpenCode 后恢复生效；Zen / Zen Go 分别使用 `https://opencode.ai/zen`、`https://opencode.ai/zen/go`；认证仍是 `api_key`，沿用模型获取、Key 池和 `auto` 协议协商，不新增持久化类型。Go 额度查询仍只匹配 Go 地址，不依赖管理账户并纳入当日活跃渠道批量额度刷新。匿名 `https://opencode.ai/inference` 通道已移除，该 URL 按普通上游处理；自 2026-10-14 起 Zen 对 `/zen` 下的免费模型请求返回 403 `FreeTierError`（来源：yetone/magpie 实测提交）。
- **System One 模型**：TypeSafe `jev-*` 列在 OpenAI 目录里，但只响应 `POST {base}/v1/systemone`，所有推理协议都返回 `ModelProtocolUnsupported`。官方 URL 的模型发现按 `jev-*` 分区：API Key 渠道剔除，System One 渠道（无 System One 目录）改读 OpenAI 目录且只保留 `jev-*`，响应协议仍报 `system_one`。
- **协议协商**：官方 OpenCode API Key 端点返回 HTTP 400 且 `error.type=ModelProtocolUnsupported` 时，代理和管理测试（`/test`、`/chat`）将其视为模型协议不支持，继续现有候选协议转换，不冷却模型或 Key；普通 400 和其他域名保留原分类。候选仍受显式 URL 协议和转换模式限制；成功代理的协议按模型缓存，该 400 不写入 404/405 的全协议不支持负缓存。
- **Header/body wire** (`opencode_compat.go`、`opencode_body.go`)：参考 [opencode2api `25afadd30345faaa9c6f18c45c0c14b176862b89`](https://github.com/jasonxu114514/opencode2api/tree/25afadd30345faaa9c6f18c45c0c14b176862b89)。只对实际选中的官方 HTTPS Zen/Go URL 和 API Key 渠道生效；同渠道其他 URL 不携带 OpenCode 指纹。代理与管理测试共用：`opencode/latest/2.0.29/cli`、`x-opencode-client=cli`、一致的四个会话头、稳定 descending `ses_` ID、40 位 hex 项目标识；移除已废弃 `x-opencode-request`。Messages 使用 `x-api-key` 和 OpenCode beta，Chat/Responses 使用 Bearer，Gemini 只认 `x-goog-api-key`（Bearer 返回 401 "Missing API key"），不叠加 Claude Code 模拟 body；beta 门控的 body 字段按最终 `Anthropic-Beta`（含 header rules）剥离。不注入 ccLoad 按上游 Key 派生的 Codex `Session-Id`，会话来自客户端会话头或调用方执行身份。合法 OpenCode 会话保留，其他会话信号确定性编码。
- **请求体兼容**：Responses 的 `max_output_tokens` 下限由 Codex 共享归一负责（见 [Codex](#codex)）；Chat 对实际出站模型以 `deepseek` 开头（忽略大小写）的请求将消息角色 `developer` 改为 `system`，保留内容、顺序及其他字段，只作用于选中的官方 OpenCode 端点，不污染换渠重试原文（参照 sub2api `ba5b21879430fdbe3ab87dc791b09bcdece5e4a7`）；对 DeepSeek/Kimi/Moonshot/MiMo 或显式启用推理的工具调用历史补 `reasoning_content`；Messages 仅对上述 vendor 的工具调用历史修复缺失/空/签名/隐藏 thinking。付费模型保留其他 provider 字段、工具定义和流式选择。顺序：与普通 API Key 渠道相同的协议级归一（Responses `prepareCodexResponsesBodyForUpstream`，Messages `normalizeAnthropicMessagesBody`；vendor 推理模型跳过 Claude 签名清理，thinking 回放由 vendor 修复负责）→ OpenCode vendor 修复 → 管理员 body rules，已处理的重试 wire 不重复应用；header rules 在指纹重建后应用，但被上游拒绝的 `x-opencode-request` 始终删除。Zen/Go 免费模型（路由后的请求模型名含 `free` 或为官方零价模型 `big-pickle`，代理与管理测试同源判定）在 body rules 后强制 `stream=true`，Chat 启用 usage；客户端同名工具定义原样保留（调用方按自己的 schema 解析参数），只从官方 MIT 工具快照追加缺失的 shell/edit/glob/grep/read（shell 描述不含宿主平台语句），未知及 namespace/custom 工具不动。`tools` 缺失或为 null 视为空数组；非数组或含非对象元素返回 400，不调用上游、不计入渠道。数据出处和许可见 `opencode_tools.LICENSE`；网关不执行这些工具。
- **Gemini wire**：官方路由是 `{base}/v1/models/{model}:{action}`，没有 `/v1beta`；代理与管理测试把 `/v1beta`、`/v1alpha` 改写到 `/v1`，精确 URL 标记不改写；协议转换的流式请求默认 `alt=sse`。免费门槛要求非空工具、`:streamGenerateContent?alt=sse` 和四个会话头，`:generateContent` 返回 `FreeTierError`：免费请求升级为流式 action 并补 `alt=sse`，不写 body `stream`；缺失的官方工具追加进首个 `functionDeclarations`/`function_declarations`（没有就新建工具对象），定义用 `parametersJsonSchema`（`parameters` 是 OpenAPI 子集，不接受 `additionalProperties`）。截至本次实测，免费模型没有 Gemini 协议，Gemini 模型（`gemini-3*`、`gemini-4-argon` 等）都是付费。

- **免费非流式响应** (`opencode_stream.go`)：保持客户端 stream 选择；上游 SSE 有界收集为原协议 JSON，再走现有跨协议转换。保留工具调用、终止原因、usage/缓存用量，缺少终态不算成功，错误 SSE 保留冷却分类；管理测试与代理同口径：SSE 错误帧按 `classifySSEErrorStatus`，其他截断记 599。代理和管理测试共用收集器与上游首内容计时；重试不重复注入工具。Gemini 按 candidate `index` 合并：相邻同类文本 part 拼接，遇到 thought 签名即断开，functionCall 等其他 part 原样保留，usage、finishReason 等元数据以后到的为准；没有 `finishReason` 也没有 `promptFeedback.blockReason` 的流不算成功。

- `opencode_responses.go` 的 namespace 兼容仅用于实际目标 URL 属于 `https://opencode.ai/zen/go`、实际上游模型为 `muse-spark-1.3-contributor` 的 Responses 请求。请求体规则之后展开顶层及动态工具声明的 namespace，同步映射工具历史和 tool_choice，保留 schema、参数和 call_id；直接工具名优先保留，名称冲突或超过 64 字节时生成稳定别名。JSON/SSE 返回恢复原工具身份，同请求局部重试保留映射。其他模型、URL 和协议不触发。
- 上游最终工具参数无效、缺少声明的必填参数或终结事件参数矛盾时记录不含参数内容的 WARN；保留上游参数和状态，不将空参数伪造成 `{}`。Debug 捕获保留上游原始响应与下游恢复后的响应。

## Codex

- **原生 Responses 推理等级**（`codex_wire.go`，参照 CLIProxyAPI `f03f4cd8b0825cc71a7eb5c85c876668160a36e3`）：仅 Codex OAuth 的 HTTP/WS 共用最终化按实际上游模型的已知等级校验顶层 `reasoning.effort` 及每条 `input[].type=configuration_update` 的等级，不合并或提升中途配置。支持的值保留；不支持的 `none` 取最低可用档，其他已知档位沿用最近等级裁剪。原生正文中的 `auto` 沿用上游兼容策略映射到 medium 再按能力裁剪，不能删除更新项的 effort 而丢掉这次变更；该策略不代表模型默认等级。模型名 `(auto)` 后缀仍在此前删除基线 effort、交回默认行为。保留 reasoning 的其他字段；缺失字段、未知模型/能力和未知等级字符串不补默认值；API Key 原生 Responses 不应用此规则。处理早于渠道 BodyRules，显式规则仍可覆盖。

- **后台生图实际格式** (`admin_testing_image.go`)：成功结果的格式以可识别图片字节优先，再采用单图或顶层上游声明；不从请求 `output_format` 推断实际输出。下载按单图MIME/格式生成链接与扩展名；未知格式不在响应中伪造声明。格式不符仍保留成功、usage及费用，不重新生成。

- **输出 token 上限**：Codex OAuth 的 HTTP/WS 共用最终化保留 `max_output_tokens`；其缺失或 null 时从数字 `max_completion_tokens`、`max_tokens` 顺序补齐，再删除两种旧字段。跨协议入口先将各协议输出上限转为 `max_output_tokens`；API Key 的原生 Responses 不补齐旧字段。所有 Codex Responses 上游（API Key/OAuth、HTTP/WS）在 `prepareCodexResponsesBodyForUpstream` 将显式正数 `max_output_tokens<16` 提升为 Responses 下限 16，OAuth 补齐旧字段后再执行一次；否则上游 400 会按模型级冷却连带切换渠道。参照 CLIProxyAPI `01b24f1f`，不因这一修复接收发到 Responses 端点的 Chat 消息结构。

- **管理页 WS 检测**：`/admin/channels/websocket-probe` 仅发起握手，不发送模型请求。API Key 渠道使用草稿 Key；已保存的 Codex OAuth 渠道通过 `channel_id` 在服务端加载并按需刷新凭据，携带账号头，前端不读取 OAuth token。两者均使用草稿 URL、代理和请求头规则。

- **Codex 模型目录**(`proxy_gemini.go`+`proxy_codex_models.go`):仅 `GET /v1/models?client_version=<非空>` 在现有 Token 渠道/模型过滤后返回 Codex `models/slug` manifest;无/空版本保留原 OpenAI/Anthropic 响应。目录只从本地已启用渠道模型名构建,不逐请求查询上游;仅列出当前 Token 可访问、至少有一条按渠道协议模式与 URL 启用状态可尝试 Codex Responses 的路由,并排除已知仅供 Images API 使用的模型、嵌入模型及目录输出模态明确不含文本的模型;未知自定义别名沿用管理员配置,不按 `gpt` 前缀过滤。此目录是配置与已知元数据的静态判断,不对每个模型发起探测请求。已知模型取静态目录的上下文与图片能力,OpenAI 静态模型再取推理档位,`gpt-6-sol/luna` 与 `gpt-4o` 使用本地预设,未知模型仅声明文本/无推理和保守的 128K 上下文。`max_context_window=null` 不阻断客户端自定义上限;ETag 按最终响应体计算,支持条件请求 304,响应标记 private/no-cache
- **Codex 推荐客户端配置**(`docs/guide/usage.md`「Codex CLI」,README 快速开始沿用同一配置):自定义 `[model_providers.ccload]`(`name = "OpenAI"`、`wire_api = "responses"`、`requires_openai_auth = true`、`supports_websockets = true`)+ 顶层 `model_provider = "ccload"` + `codex login --with-api-key`。自定义 provider 不发 `Version`,上游因此不按 `minimal_client_version` 门控;WebSocket 必须靠 `supports_websockets = true` 显式开启。文档不再推荐内置 `openai` provider + `openai_base_url`
- **Codex 套餐与 Ultrafast**：套餐标识按上游原值保存，不把未知 SKU 改称 Pro；导入时的预置模型目录只对明确 `free` 应用已登记限制，不靠套餐名授予 Ultrafast。展示参照 sub2api `42bc7f6cffe24bcb471608e48e66b4a0afa1f882` 的 `planType.ts`：`prolite/pro/promax` 为 Pro 100/200/500，Business、Enterprise、Edu 各 SKU 分别显示，未知值原样保留。管理员为 Codex OAuth「获取模型」时读取账号 `/models?client_version=...`，通过凭证 CAS 保存绑定账号、用户、套餐、端点的 `model_manifest`；端点身份不含 `client_version`，内建版本升级不作废已有快照。手动额度重置只推进账本纪元、不作废快照；轮询检测到的账号/套餐纪元重启会清空快照，采样早于写入时纪元的结果拒绝保存。上游 `/models` 不可达时「获取模型」直接报错，不回退预置目录。普通公开模型列表只读取快照，不触发上游查询，并且每条路由只按其渠道自身模型计算 `service_tiers`，多路由声明不一致时返回未知。Astra 的官方 OpenAI API Key 路由可声明 Ultrafast，OAuth 必须由对应账号 manifest 明确声明；自定义中转和多个候选路由不得仅凭名称推定支持。`service_tiers` 的未知、空列表和明确列表保留不同语义；别名按实际目标判断。Astra Ultrafast 计费参见计费契约。
- **Codex 图片模型**(`codex_images.go`、`admin_testing_image.go`):`gpt-image-2.5`、`gpt-image-2.6` 及各自 `-flare`、`-sunburst` 变体的公开 `/v1/images/generations`、`/v1/images/edits` 在 auto/local 模式按渠道 Codex 能力接入原生 OpenAI Images wire，使用 Codex OAuth 认证，URL 从 Responses 端点切到同 base 的 `/images/generations`、`/images/edits`。顶层 model 保留图片模型并去除路由/思考后缀；管理页共用模型归一、URL 和 JSON 请求构造。编辑 JSON 保留图片引用和 mask，multipart 的 image/image[]、mask 文件转 data URL；不下载远程图片，不创建临时文件。保留 JSON/SSE 响应与正整数 n，不在网关做多次生图展开。两款 `-2026-09-08` 快照继续仅在 generations 使用原有 Luna Responses 工具桥接；原生 Responses 文本主模型不替换。`gpt-image-1.5`、`gpt-image-2` 的管理页直连维持原状。参考 CLIProxyAPI `d1a024e9400bc65bd78ccd908945cf2eacc2835e`（checkout `e8399ffe8aeb48917df1730db93e5b5071c05cd1`）；这是 app 层移植，不更新转换核心快照。2.6 系列参照 CLIProxyAPI `7a7d37ecb5c61d69413d19d7bce085a82740f5ca`，同样加入默认模型目录并从 free 计划目录排除。
- **Codex 输入条目 ID**（`codex_upstream_websocket.go:sanitizeCodexInputItemIDs`，参考 CLIProxyAPI `606e667a8`）：HTTP 与原生 WebSocket 共用前缀、长度和字符规范化；`[a-zA-Z0-9_-]` 以外字符替换为 `_`，截短前缀同样清理。碰撞哈希以替换前的前缀归一 ID 为种子，预留已有合法 ID，重复条目稳定映射，不改 `call_id`。
- **Codex 窗口头**(`codex_credentials.go`+`codex_upstream_websocket.go`):`X-Codex-Window-Id` 按 CLIProxyAPI 默认行为仅随 HTTP 上游请求透传;准备原生 WebSocket 时移除从 HTTP 候选继承的窗口头,再单独应用该头的渠道自定义规则。WebSocket 握手失败回退 HTTP 时保留原窗口头(Codex OAuth 为账号作用域映射后的值);窗口变化不改变 WebSocket 默认连接复用或执行会话身份
- **Codex 上游 Header 契约**(`codex_credentials.go`+`codex_upstream_websocket.go`):不走通用反代透传;HTTP 只接收 Codex 客户端白名单,静态 Key 与 OAuth 都只用 `Authorization: Bearer`;当 `User-Agent` 能识别为官方 Codex 客户端时原样保留 UA;客户端 `Version` 原样保留、不抬高也不补写(官方内置 `openai` provider 总会发送,自定义 provider 不发);`Originator` 按 UA 首段(`/` 之前)配对重建以贴合原生客户端。实测(2026-09)上游不校验 Originator、无全局版本下限,只按模型 `minimal_client_version` 对 `Version` 头门控(低于则 400,缺失则不门控),所以从 UA 补 Version 只会凭空增加拒绝。缺少官方 UA 或任意第三方值时,整体回退内建 UA/Version/Originator 三元组(版本见 `codexauth.DefaultClientVersion`),不做部分替换;内建版本须随官方发行更新,`/models` 的 `minimal_client_version` 不可靠(2026-09 实测 gpt-6.1-sol 标 0.153.0,但 0.158.0 仍被拒、0.159.x 通过);不注入官方客户端没有的 `Connection: Keep-Alive`。白名单含官方按请求发送的 `X-Codex-Parent-Thread-Id`/`X-OpenAI-Subagent`/`X-OpenAI-Memgen-Request`(HTTP 另含 responses-lite 头,见下条);`x-oai-attestation` 与 `x-openai-internal-codex-residency` 不透传:前者是客户端自身 ChatGPT 账号的设备证明,后者是客户端组织的数据驻留声明,挂到渠道账号上都是错配。HTTP 与原生 WebSocket 都只保留规范 `Session-Id`+`Thread-Id`：实测（2026-11，codex-cli 0.166.0）官方客户端 HTTP 请求与 WS 握手只发 `session-id`/`thread-id`，下划线头已于 openai/codex#22193 删除，`session_id`/`thread_id` 仅是请求体 `client_metadata` 的键；客户端旧 `Session_id` 不转发、不参与补头判断，也不生成 `Session_id`/`Conversation_id` 别名。静态 Key（中转）渠道上 `prompt_cache_key` 只作缓存提示，不得提升为规范执行身份（含管理测试）；否则链式网关会把独立连接并入同一 transcript。OAuth 直连官方上游，缺少 `Session-Id` 时按 CPA 用最终（账号映射后）`prompt_cache_key` 作 `Session-Id`，无缓存键才随机生成：原生 WS 握手头参与连接复用，逐次随机会让同一会话每轮重新握手并全量回放。WebSocket 额外接收 turn state/timing/`OpenAI-Beta`,握手前删除 HTTP 传输头并归一 `OpenAI-Beta`;渠道自定义 Header 规则仍可显式增加非认证 Header
- **Codex 渠道测试默认详细度**(`internal/testutil/templates/codex.json`):测试和渠道对话使用 `text.verbosity=medium`，兼容仅支持该值的 `gpt-6-chat-thinking`。普通代理不强制改写客户端传入的详细度。
- **Codex responses-lite 信号**(`codex_wire.go:codexResponsesLiteRequested`):官方 Codex 对 `use_responses_lite` 模型按传输发送信号——HTTP 用 `X-OpenAI-Internal-Codex-Responses-Lite: true` 头,WebSocket 用 `client_metadata.ws_request_header_x_openai_internal_codex_responses_lite="true"`。任一形态都视为开启:Codex OAuth HTTP 请求由最终 body 补设该头(与路由提示同一步,早于 Header 规则),HTTP 传输边界(`prepareCodexOAuthHTTPBody`)删除 metadata 键;原生 WebSocket 握手(`codexWebsocketHeaders`)删除该头,不计入连接哈希,由 `normalizeCodexWebsocketResponsesLite` 写入每个请求的 metadata。开启时 `parallel_tool_calls` 置 false

- **Codex OAuth 账号作用域身份**(`codex_account_identity.go`,对齐 sub2api `openai_codex_account_identity.go`):客户端 installation/session/thread/turn/window/request ID 及父线程/派生线程/父 turn/根 turn/上下文窗口 ID(`codexAccountIdentityFields`)以 `chatgpt:<CodexAccountID>[:user:<CodexUserID>]` 为命名空间确定性映射,覆盖出站白名单头(`Session-Id`/`Thread-Id`/`X-Codex-Window-Id`/`X-Codex-Parent-Thread-Id`/`X-Client-Request-Id`/`X-Codex-Turn-Metadata` 内嵌 JSON)与 body 的 `prompt_cache_key`、`client_metadata`(含内嵌 turn metadata);同账号稳定、跨账号不可关联。映射不分字段种类,客户端原本相等的字段映射后仍相等。值按 `:` 分段,只映射规范 UUID 段、其余段原样保留:窗口 `<thread_id>:<代数>` 与内部会话 `prompt_cache_key`/`Session-Id` `<source>:<parent_thread_id>`(如 `guardian:`)映射后仍对应 thread/父线程头。UUID 段保留版本与变体位,UUIDv7(官方 session/thread/turn)还保留 48 位毫秒时间戳、只替换随机位;不含 UUID 段的值整体映射为 v4。重试回放的 wire body(`replayBodyRulesApplied`)已映射,不得二次映射,缺会话头时 `Session-Id` 跟随最终 `prompt_cache_key`,首轮与回放一致;渠道 Header 规则写入的值原样发送,原生 WS 从客户端头补回的值同样先映射。无账号 ID 时不映射
- **Codex OAuth turn-state 来源标签**(`codex_account_identity.go`):`x-codex-turn-state` 是上游按账号签发的 sticky routing 令牌,官方客户端每个 turn 只保存首个值并在该 turn 内回带(HTTP 头、WS 握手头、WS `client_metadata`)。官方客户端从 HTTP 响应头、WS 握手头或 WS `response.metadata` 事件读取令牌;HTTP SSE 的 metadata 事件不会被客户端用作令牌来源。上游响应头(HTTP 响应,或原生 WS 合成响应:`cloneCodexQuotaHeaders` 按 `x-codex-` 前缀保留握手头)在 `handleResponse` 前打标签;原生 WS 的 `codex.response.metadata`/`response.metadata` 事件 `headers` 在中继循环打标签,两类事件都打,因为其他客户端可能读 `codex.response.metadata`,未打标签的值出站会原样透传。前缀为 `ccl1.<命名空间 sha256 前 8 字节 hex>.`;出站时标签匹配当前账号才去标签发出,属于其他账号则删除,无标签值原样透传(非 OAuth 渠道、链式 ccLoad、无账号 ID 的 OAuth 渠道均不打标签也不解析)。下游 WS 在选路前已完成升级,`bridgeWriter` 丢弃响应头;因此下游 WS、上游握手回退 HTTP 时 turn-state 无法回传(只丢粘性,不破坏账号隔离)。标签随令牌流转,无服务端状态,不依赖失败切换时机,也不受客户端 OnceLock 只保留首个值影响

- **Codex 工具 schema 规整**(`codex_tool_schema.go`,移植 CPA `helps/codex_tool_schema.go`,属执行器行为,不进快照 manifest):`prepareCodexResponsesBodyForUpstream` 中对 function/custom 及 namespace 内工具参数,把 ≥8 个分支、仅含 const/description/title 且值唯一的 oneOf/anyOf 折叠为 `enum`(已有 enum 仅在集合相等时删除联合),并按 schema 关键字位置删除含 `\p{`/`\P{`/`\0` 的 pattern;用户数据里的同名键与未证明等价的结构原样保留
- **Codex 令牌刷新**(`codexauth/service.go`,对齐官方 rust-v0.157.1 `request_chatgpt_token_refresh`):refresh 用 JSON body(`client_id`/`grant_type`/`refresh_token`,不带 scope);授权码交换仍是 form。两者都带官方 `Originator`/`User-Agent` 与 `Accept: */*`
- **Codex 刷新时机**(`codex_credentials.go`):请求时距到期不足 24h 即提前刷新；新 token 寿命仍不足 24h 时，同一 access token 退避 5 分钟。导入仍只用 5 分钟偏差判断是否立即刷新。所有刷新入口必须传入权威 SQL journal：按 `SHA256(client_id + NUL + refresh_token)` 在网络发送前以随机 owner 原子 claim，成功结果先保存 receipt，再更新渠道凭据。已建立连接后的传输/读体/解码失败、未取得可信成功结果或保存失败后不重放旧 grant；401 强制刷新、重启、重复导入、删除再建渠道均不能解除 claim。已有成功 receipt 可恢复轮换结果；同 grant 的 receipt 过期后要求恢复或重新授权，不再次兑换。刷新 POST 禁止跟随重定向。
- **Codex 刷新发送前失败**（参照 CLIProxyAPI `1f5bf2a569c35eec45637836c440954c5cf1ddae`）：请求构造失败、发送前取消，以及未取得连接且未读取正文的 DNS/拨号/握手失败，可由本次随机 owner 条件释放未完成 claim，再沿现有退避等待后续请求重试。释放失败仍视为结果不明；不按时间回收，不释放已有 receipt 或其他 owner 的记录。SQL journal 增加可空 `claim_owner`，旧 NULL owner 记录继续封锁；历史未知结果不自动解锁。刷新请求禁用 GetBody，避免传输层隐式重放；缺少可信发送阶段信息的错误仍保守归为未知。
- **Codex 刷新恢复**：不确定结果仅封锁刷新 grant，仍有效且未被上游拒绝的 access token 可继续推理；明确永久拒绝继续沿既有凭证快照 CAS 停用规则。`refresh_token_reused`、`refresh_token_invalidated`、`token_revoked` 不扩散到其他 provider；`invalid_client` 不作为个人凭据失效的证据。管理员列表/详情的 `codex_requires_reauthorization` 只提示恢复，不暴露错误正文或 token。重新授权须取得新 grant；journal 必须与凭据一同备份、恢复。混合存储以本地 SQLite 为权威；从远端副本首次恢复到新 SQLite 时，对缺少刷新记录的旧 Codex grant 预置 claim，要求重新授权，仍可使用有效 access token。
- **Codex 凭证两种形态**(`codexauth/credential.go`+`admin_codex_auth.go:HandleCreateCodexPersonalAccessToken`,`POST /admin/codex/personal-access-token`):OAuth 与个人访问令牌(PAT)共用 `auth_type=codex_oauth`,靠凭证内 `AuthMode=personalAccessToken` 区分,别新造 auth_type。PAT 必须 `at-` 前缀,导入时走 `whoami` 端点校验并解析账号身份,按账号复用或新建渠道(上游 401/403 返回 400,其余网络/服务端错误返回 502);PAT 是静态令牌,`Refresh` 直接返回 `ErrPersonalAccessTokenCannotRefresh`,一旦被上游拒绝即终态,触发上面的渠道禁用
- **Responses 路径别名**(`protocol/types.go`+`server.go`+`codex_wire.go:normalizeCodexClientPath`):下游 `/v1/responses`、`/v1/codex/responses`、`/backend-api/codex/responses` 是同一 canonical 端点,GET 走 WebSocket 升级、POST 走 SSE fallback,`DetectRequestFamily` 一律识别为 Responses。上游协议为 Codex 时转发前把别名归一回 `/v1/responses`,避免别名泄漏进上游 URL;`Exact` 标记的 OAuth 官方 URL 不拼接路径,不受影响。新增 Responses 入口路径必须同时登记这三处
- **Codex 与 Anthropic 上游 TLS** (`codex_utls_transport.go`): 普通 HTTP 请求对 `https://chatgpt.com` 使用 Chrome uTLS，按 HTTP/2 → uTLS HTTP/1.1 → 标准 HTTP/1.1 降级；`https://api.anthropic.com`、`https://claude.ai`、`https://platform.claude.com` 使用相同的 Node 风格 HTTP/1.1 uTLS 与每个 Transport 的 32 项 TLS session cache；Messages/count_tokens 的头顺序表（`anthropicClaudeCodeHeaderOrder`）同时决定线上头名大小写（Go 入站会规范化头名，只能在 `httpwire` 写出时还原），原生透传的 `x-claude-code-*`/`x-claude-remote-*` 等小写头须逐个登记，未登记的头保持原写法排在最后。Anthropic ticket 随账号、代理与连接代际隔离；其他 Host 走标准 Transport。uTLS 继承环境/渠道代理、Host 覆盖、证书校验和握手超时，连接池跟随 `upstream_connection_reuse_limit_seconds` 整代轮换；原生 WebSocket 使用独立 Dialer。
- **OAuth 连接池隔离** (`server.go:getClientForChannel`): 所有 OAuth 渠道经此入口发出的 HTTP 数据、凭证刷新、额度及模型目录请求，使用按账号和渠道代理 URL 隔离的 Client/Transport；优先取稳定账号身份，避免 access token 轮换重建连接池，同渠道更换账号必须切换池。Antigravity 按 refresh token 隔离，Anthropic 及其他 OAuth 还包含渠道 ID；API Key 渠道沿用默认或按代理共享的池。Codex 原生 WebSocket 的物理连接独立属于执行会话，复用时核对渠道和认证信息。
- **Codex OAuth 请求体 zstd**(`codex_wire.go:compressCodexOAuthResponsesBody`,对齐官方 rust-v0.157.1 `responses_request_compression`):仅 Codex OAuth 的 HTTP `POST .../responses`(路径恰为 `/responses`,不含 `/responses/compact`)在唯一出口 `doReservedUpstreamRequest` 发送前压缩为 zstd level 3、无校验和,并设 `Content-Encoding: zstd`;客户端已带编码则不动。API Key 渠道与原生 WebSocket 帧不压缩。调用方持有的明文 body 仍用于调试日志与失败重放,重放经同一出口重新压缩
- **Codex OAuth Cloudflare Cookie**(`codex_cookie_jar.go`,对齐官方 `chatgpt_cloudflare_cookies.rs`):只对 https 的 `chatgpt.com`/`chat.openai.com`/`chatgpt-staging.com` 及 `*.chatgpt.com`/`*.chatgpt-staging.com` 保存官方白名单(`__cf_bm`/`__cflb`/`__cfruid`/`__cfseq`/`__cfwaitingroom`/`__oailb`/`_cfuvid`/`cf_clearance`/`cf_ob_info`/`cf_use_ob`/`cf_chl_*`),其余 Cookie 丢弃。官方是进程级存储,ccLoad 改为挂在上面按账号+代理隔离的凭证 Client 上,避免跨账号关联;`codexWebsocketDialer` 取同一 Client 的 jar,HTTP 与 WebSocket 握手共用。access token 刷新不换池,Cookie 保留
- **Codex OAuth 不发 `Accept-Encoding`**(`server.go:getClientForChannel`):官方 reqwest 未编入解压 feature(lock 中 reqwest/tower-http 无 `async-compression`/`flate2`),请求不带该头。Codex OAuth 凭证池的 Transport 设 `DisableCompression`,uTLS H2/H1 与连接代际轮换从它继承,覆盖数据、刷新、额度与模型目录请求;管理测试同样不补 `identity`(`admin_testing.go:setAdminTestAcceptEncoding`,其他渠道仍强制 `identity` 以规避兼容网关残留 gzip 标记);其他渠道代理请求保持 Go 默认 gzip 协商
- **Codex 多代理 v2**(`codex_multi_agent_v2.go`):只有一条规则——**Codex 协议 → 非 Codex 协议**的 `agent_message` 与 collaboration 工具可移植性改写,按官方 Codex 客户端 User-Agent(`isCodexMultiAgentClient`)门控,其他调用方一律原样透传,避免把网关模型目录写进第三方请求体。Codex → Codex 透明直通。不存在命名空间改写-还原对:非 Codex 源协议转成 Codex 后是扁平 `tools` 数组,不携带 `type=namespace` 包装,无从改写
