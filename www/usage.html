API Usage

API Usage

ccLoad exposes Anthropic, OpenAI, Gemini, and Codex-compatible endpoints, including Responses WebSocket, thinking suffixes, and the Images API. Clients only need a new base URL and token.

Anthropic Messages OpenAI Chat Gemini v1beta Codex Images API

Before calling the API

Create an API access token in the admin console, then point the client base URL at ccLoad. Do not send upstream provider keys to clients; clients should only hold ccLoad tokens.

Log in to the admin console

Open http://localhost:8080/web/ and log in with CCLOAD_PASS.

Add channels

Open the channel page and configure the upstream protocol, URL, API key, priority, models and limits. Separate multiple URLs with commas.

Create access tokens

Create client tokens on the token page. Restrict models, choose a channel allowlist or denylist, and cap cost or concurrency when needed. An empty channel list is unrestricted in either mode. Proxy endpoints return 401 when no token exists.

Connect Claude Code and Codex

Replace your-api-token with the ccLoad token from the previous step. On a server, replace localhost with the server IP or domain.

1. Edit ~/.claude/settings.json (%USERPROFILE%\.claude\settings.json on Windows). Create it if it does not exist; if it already has other settings, merge just these two entries into env. Leave /v1 off the address; Claude Code appends /v1/messages itself. Settings in this file apply to every terminal and IDE extension.

json 
{
  "env": {
    "ANTHROPIC_BASE_URL": "http://localhost:8080",
    "ANTHROPIC_AUTH_TOKEN": "your-api-token"
  }
}

2. Make sure the model names match. Besides the main model, Claude Code uses a Haiku model (such as claude-haiku-4-5) for background tasks like title generation, and every one of these names must appear in some channel's model list. If your channels lack them, point them at models your channels do have; the full file becomes:

json 
{
  "env": {
    "ANTHROPIC_BASE_URL": "http://localhost:8080",
    "ANTHROPIC_AUTH_TOKEN": "your-api-token",
    "ANTHROPIC_DEFAULT_OPUS_MODEL": "model-name-from-your-channel",
    "ANTHROPIC_DEFAULT_SONNET_MODEL": "model-name-from-your-channel",
    "ANTHROPIC_DEFAULT_HAIKU_MODEL": "model-name-from-your-channel"
  }
}

3. Verify: run claude -p "hello"; a reply means it works. In interactive mode, /status shows the current base URL.

1. Log in with your ccLoad token. This replaces any existing ChatGPT login in Codex; the same command works in Windows PowerShell.

bash 
echo your-api-token | codex login --with-api-key

2. Edit ~/.codex/config.toml (%USERPROFILE%\.codex\config.toml on Windows). If the file does not exist, create it and paste everything below. If it already has content, add the two parts separately: the model_provider = "ccload" line at the very top of the file (before any [...] section, or it will not take effect), and the whole [model_providers.ccload] block at the end of the file.

toml 
model_provider = "ccload"

[model_providers.ccload]
name = "OpenAI"
base_url = "http://localhost:8080/v1"
wire_api = "responses"
requires_openai_auth = true
supports_websockets = true

base_url must include /v1. requires_openai_auth = true makes Codex use the token from step 1, and supports_websockets = true enables Responses WebSocket.

3. Verify: run codex exec --skip-git-repo-check "hello"; a reply means it works.

If you use the app-server daemon (for example codex agents or codex remote-control), not every change applies right away: sessions already open keep the old config.toml settings, and after codex login with a new token the daemon keeps the old token until it restarts. After changing the config or logging in again, run codex app-server daemon restart. If codex app-server daemon version reports failed to connect, the daemon is not running and needs no restart.

Endpoint Reference

All four core client protocols can use every model-compatible channel. In automatic mode, ccLoad tries the client protocol first, then probes OpenAI, Anthropic, Codex, and Gemini without retrying the client protocol. It advances only when the request has not produced output and the endpoint reports a capability mismatch, or when the request cannot be represented in that protocol.

Client Endpoint Purpose
Anthropic / Claude Code POST /v1/messages Messages API, streaming and non-streaming.
OpenAI-compatible clients POST /v1/chat/completions Chat Completions, suitable for OpenAI SDKs with only a base URL change.
Codex clients POST /v1/responses Responses-compatible endpoint for Codex-style requests and streams.
Codex WebSocket clients GET /v1/responses Authenticated Responses WebSocket; aliases are GET /v1/codex/responses and GET /backend-api/codex/responses.
Codex Alpha Search POST /v1/alpha/search Native Codex search passthrough. Only resolved Codex upstreams are eligible.
Images API POST /v1/images/generations OpenAI Images-compatible. xAI conversational models at grok-4.6 and later are bridged to the Responses image_generation tool.
Gemini clients POST /v1beta/models/{model}:generateContent Gemini generateContent-compatible endpoint.
Token count POST /v1/messages/count_tokens Local token estimation without forwarding to upstream.
Health check GET /health Process liveness check for container probes.

Model thinking suffix

Append a thinking level to any model name. ccLoad strips it for routing, then writes the matching thinking fields for the protocol actually forwarded upstream.

Accepted suffixes

  • Levels: (minimal) (low) (medium) (high) (xhigh) (max). A level beyond the upstream model clamps to the nearest supported tier.
  • Disable: (none) or (0).
  • Auto: (auto) defers to the upstream default.
  • Numeric budget: (16384) becomes Anthropic budget_tokens or Gemini thinkingBudget.

Not a model identity

  • Request claude-sonnet-4-6(high), gpt-5.2(xhigh), or gemini-3.1-pro(8192).
  • Routing, auth, cooldown, logging, and the upstream model name always use the base name. Channel model lists do not need suffixed entries.
  • HTTP proxy, Responses WebSocket, and admin channel tests all honor the suffix. Channel custom request rules run later and can override the fields it writes.

First-party account channels

Import credentials in the admin console. Clients only hold ccLoad tokens. OAuth authorization and token refresh still use the provider's official endpoints.

Codex / Anthropic / Antigravity / xAI

  • Import OAuth credentials, or a Codex PAT that starts with at-.
  • Anthropic Messages requests automatically remove blank text blocks, including those inside tool results, before forwarding.
  • Batch-refresh quota windows from the channel card. Permanently rejected refreshes disable the channel without cooling it.
  • Optional system settings CODEX_BASE_URL, ANTHROPIC_BASE_URL, XAI_BASE_URL, and ANTIGRAVITY_URL override data-plane addresses only.

CodeBuddy

  • Scan to sign in, or import workbuddy.json or credential JSON. Tokens refresh automatically.
  • Models are fetched from the account when creating a channel. Reauthorizing an existing channel preserves its model configuration.
  • Refresh balances from the channel card: personal accounts show resource packs, and enterprise accounts show their quota. Daily check-in is available for the China edition; international editions do not support it.

Z.ai Coding Plan

  • Complete the browser authorization flow, or import a Coding Plan API key when the provider OAuth poll endpoint is unavailable.
  • The model catalog is loaded from the account, then models.dev, then the built-in list.
  • Quota windows are shown on the channel card and are not billed as standard cost.

Cursor

  • Open Cursor Dashboard → Integrations → User API Keys to create a key, then paste it into the channel dialog. Submitting an empty field opens that dashboard. Browser session tokens and Cursor CLI credentials are not supported.
  • ccLoad locates or installs the pinned official SDK Bridge in the background. Inference does not use HTTP forwarding.
  • The SDK Agent allows only Cursor's mcp capability group, which exposes SDK custom tools through the synthetic custom-user-tools server while keeping shell, file, and other built-ins disabled. Native callbacks remain isolated by Agent and call ID.

Zed

  • Native app sign-in exchanges an ephemeral RSA public key on a random loopback port; the callback token is decrypted into a long-lived native credential and the private key is never persisted.
  • Trial access depends on a real Zed installation system_id. Without one, ccLoad still allows sign-in and lets the upstream decide account eligibility.
  • A fixed exact /completions upstream runs Codex-protocol local transforms with WebSocket disabled; quota is read from /client/users/me.

Codex Responses WebSocket

The downstream client keeps one authenticated WebSocket while each selected upstream candidate may use native Codex WebSocket or the existing HTTP/SSE bridge.

Channel and session setup

  • Upgrade GET /v1/responses, GET /v1/codex/responses, or GET /backend-api/codex/responses with a ccLoad access token.
  • Enable websockets only on channels whose upstream protocol is Codex. Other candidates continue through HTTP/SSE.
  • Keep the API token and Session-Id header stable across reconnects. When Thread-Id is present, ccLoad combines it with Session-Id so concurrent agent transcripts and turn locks stay isolated. Request-body cache hints never identify an execution session.
  • New installs retain 1024 execution sessions with a 256 MiB transcript budget and a 15-minute idle TTL. Downstream connections default to 1024 globally and 64 per token.
  • upstream_connection_reuse_limit_seconds can rotate old upstream HTTP and WebSocket connections. Active turns drain first; a new native WebSocket reconnects on demand and replays the retained transcript.

Failover boundary

  • Before semantic output, HTTP/SSE → HTTP/SSE, native WebSocket → HTTP/SSE and native WebSocket → native WebSocket failover happens inside ccLoad.
  • HTTP/SSE → native WebSocket returns a retryable 502/server_error/upstream_unavailable event and closes with code 1011; the client must reconnect and replay the complete request.
  • After any semantic output, ccLoad does not switch transports or replay, preventing duplicate text, tool calls and charges.
  • Before output, ordinary upstream HTTP 413 follows the 400 model-scoped cooldown and channel failover policy. Context-length errors return to the client directly. A WebSocket 1009 close (message_too_big) preserves the close behavior without trying another channel; reduce the request size before retrying.

Built-in Search Across Protocols

ccLoad keeps model search requests in the native shape required by the runtime upstream protocol. It does not pretend web search is a normal function tool.

Protocol Search request shape Transform behavior
OpenAI Chat "web_search_options": {} OpenAI upstreams receive native Chat Completions search options; Codex web_search tools are converted to this shape when forwarding to OpenAI.
Codex Responses "tools": [{"type": "web_search"}] Codex upstreams receive the Responses tool form, including search options and tool choice when present.
Codex Alpha Search POST /v1/alpha/search Native passthrough only. This endpoint is never translated to another protocol, and its model field is optional.
Gemini "tools": [{"googleSearch": {}}] Gemini channels receive the Google Search tool shape instead of OpenAI or Codex fields.
Anthropic "web_search_20250305" Anthropic channels receive the Anthropic web search tool form with the standard tool name.
Search remains an upstream capability. If the selected provider, model or route does not support built-in search, disable search for that request or channel instead of expecting ccLoad to emulate browser access.
Antigravity Responses search. Requests containing only native web_search tools use the dedicated Gemini search route when tool_choice permits it. Domain filters are preserved, and responses include search calls, citation annotations and search usage. Mixing function tools or setting tool_choice: "none" disables that route.

API Examples

The Authorization header below uses a ccLoad access token, not an upstream provider key.

bash 
curl -X POST http://localhost:8080/v1/messages \
  -H "Authorization: Bearer your_ccload_token" \
  -H "Content-Type: application/json" \
  -H "anthropic-version: 2023-06-01" \
  -d '{
    "model": "claude-sonnet-4-6(high)",
    "max_tokens": 1024,
    "messages": [
      {"role": "user", "content": "Hello from ccLoad"}
    ]
  }'
bash 
curl -X POST http://localhost:8080/v1/chat/completions \
  -H "Authorization: Bearer your_ccload_token" \
  -H "Content-Type: application/json" \
  -d '{
    "model": "gpt-5",
    "messages": [
      {"role": "user", "content": "Search for current ccLoad release notes"}
    ],
    "web_search_options": {},
    "stream": true
  }'
bash 
curl -X POST http://localhost:8080/v1/responses \
  -H "Authorization: Bearer your_ccload_token" \
  -H "Content-Type: application/json" \
  -d '{
    "model": "gpt-5-codex",
    "input": [
      {
        "type": "message",
        "role": "user",
        "content": [
          {"type": "input_text", "text": "Search for current ccLoad release notes"}
        ]
      }
    ],
    "tools": [{"type": "web_search"}],
    "tool_choice": "auto",
    "stream": true
  }'

Codex Alpha Search

This endpoint preserves the native Codex search payload. The model field is optional, and only channels whose resolved upstream protocol is Codex can handle the request.

bash 
curl -X POST http://localhost:8080/v1/alpha/search \
  -H "Authorization: Bearer your_ccload_token" \
  -H "Content-Type: application/json" \
  -d '{
    "query": "golang channels"
  }'
Regular channel base URLs automatically append /v1/alpha/search. An exact URL ending in # must already point to that endpoint, for example https://upstream.example.com/v1/alpha/search#. ccLoad removes prompt_cache_key and prompt_cache_retention before forwarding.
bash 
curl -X POST "http://localhost:8080/v1beta/models/gemini-2.5-pro:generateContent" \
  -H "Authorization: Bearer your_ccload_token" \
  -H "Content-Type: application/json" \
  -d '{
    "contents": [
      {
        "role": "user",
        "parts": [{"text": "Hello from Gemini-compatible client"}]
      }
    ]
  }'
bash 
curl -X POST http://localhost:8080/v1/images/generations \
  -H "Authorization: Bearer your_ccload_token" \
  -H "Content-Type: application/json" \
  -d '{
    "model": "grok-4.6",
    "prompt": "A red fox in snow",
    "size": "1024x1024"
  }'
This is the OpenAI Images API, not xAI's native grok-imagine media API. For conversational models at grok-4.6 and later, ccLoad bridges the request into an xAI Responses image_generation tool call. Non-streaming requests aggregate into standard Images JSON; streaming requests emit partial_image / completed SSE. Body size is capped by max_image_body_bytes.
bash 
curl -X POST http://localhost:8080/v1/messages/count_tokens \
  -H "Authorization: Bearer your_ccload_token" \
  -H "Content-Type: application/json" \
  -d '{
    "model": "claude-sonnet-4-6",
    "messages": [
      {"role": "user", "content": "Count this locally"}
    ]
  }'

How to use the admin console

The console is not decorative; it is the runtime control plane for channel configuration, token limits, log tracing, trend statistics and debug logs.

  • Channels: create, edit, delete and test upstream channels; import OAuth / PAT / Cursor / Z.ai / Zed credentials; pause individual models; set per-key model allowlists; detect native WebSocket support; configure provider-specific cooldown rules and daily scheduled checks; import or export CSV.
  • Tokens: assign client tokens with model, channel allowlist or denylist, cost and concurrency restrictions.
  • Logs: filter requests by status code, channel, model and token to locate failures.
  • Overview: compare traffic by client protocol and inspect seven-day service health.
  • Stats: inspect requests, tokens, cost, first-byte latency and channel health.
  • Trends: observe RPM, cost and latency by time range.
  • Model test: run chat-style requests or test models by channel through the real proxy path, including thinking suffixes, built-in search, and image generation. API-key choices show the masked key, its note and cost multiplier to help select the intended credential.
  • Cache metrics: cache-read and cache-write statistics follow the usage returned by the upstream, including compatible providers and custom model names.

Channel Management API

The web UI is best for daily operations; bulk import, automation and migration can call the admin API directly.

Add a channel

bash 
curl -X POST http://localhost:8080/admin/channels \
  -H "Authorization: Bearer admin_session_or_token" \
  -H "Content-Type: application/json" \
  -d '{
    "name": "Claude-API",
    "urls": [
      {"url": "https://api.anthropic.com", "protocols": ["anthropic"]}
    ],
    "protocol_transform_mode": "auto",
    "api_key": "sk-ant-xxx",
    "priority": 10,
    "models": [
      {"model": "claude-sonnet-4-6"},
      {"model": "claude-opus-4-6", "disabled": true}
    ],
    "enabled": true
  }'

CSV import/export

bash 
curl -H "Authorization: Bearer your_token" \
  http://localhost:8080/admin/channels/export > channels.csv

curl -X POST -H "Authorization: Bearer your_token" \
  -F "file=@channels.csv" \
  http://localhost:8080/admin/channels/import

Channel management accounts

api_key channels can attach a New API or Sub2API management account for balance checks and daily check-in. Profiles: new_api (user ID, check-in + balance), sub2api (balance only) and sub2api_pro (check-in + balance). Writes are compare-and-swap and serialized per channel.

bash 
# Manual check-in and balance refresh
curl -X POST -H "Authorization: Bearer your_token" \
  http://localhost:8080/admin/channels/42/management-account/checkin

curl -X POST -H "Authorization: Bearer your_token" \
  http://localhost:8080/admin/channels/42/management-account/balance

# CSV carries management_daily_checkin_enabled and
# management_daily_checkin_time columns. Daily check-in runs on a
# per-channel scheduler and writes log_source=checkin audit entries.

Debug from logs, not guesses

ccLoad records custom status codes such as 499, 596, 597, 598 and 599 to separate client cancellations, quota exhaustion, SSE errors, first-byte timeouts and stream interruptions.

429 has two explicit success-rate scopes. UI timeline success rate includes 429 as an error and exposes it again as the rate_limited subset for pure rate-limit coloring; health-score sorting excludes 429 so key-level throttling does not demote an otherwise healthy channel.
